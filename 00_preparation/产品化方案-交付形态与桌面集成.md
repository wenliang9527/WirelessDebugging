# 产品化方案:交付形态与桌面集成(2026-10-28)

> 目标:把现在"散在三个目录、要记四条命令、IP 变了就得改脚本"的东西,收成**同事拿到就能用**、**可以卖**的一个包。
> 本文只给方案与取舍,不含实现细节。P4 文档(用户手册/排障表)在本文之后做。

---

## 0. 先说三个结论

1. **无线优先设置**:当前 `@PRIO` 只能置顶一次,而 `@CONNECT` 会把它顶掉。方案是把"优先级"从**隐式副作用**改成**显式状态**——列表里每条带一个「优先」标记,由 GUI 编辑,固件按标记选人,`@CONNECT` 不再改变顺序。
2. **环境集成**:不要试图把 usbip / elaphureLink / OpenOCD 塞进一个 exe。它们各有系统级依赖(驱动、注册表、.NET),硬塞必然变成"装不上/被杀软拦/卸载不干净"。正确做法是**统一入口 + 自动配置 + 状态可视**,工具本身保持独立目录。
3. **出售的合规红线**:固件 MIT 可用;elaphureLink BSD-2 可用但要留版权声明;**openocd-elaphurelink 与 usbip-win 是 GPL-2,不能和你的闭源 GUI 打进同一个 exe**,只能作为**独立程序随包分发**并附源码/许可。这条决定了交付形态,不是可选项。

## 1. 无线优先:从"置顶"到"优先标记"

### 1.1 现在的问题(已实测)

| 行为 | 结果 |
| --- | --- |
| `@PRIO idx=1` 把 SENLO/2 置顶 | 成功,重启后仍第一位 ✅ |
| 之后 `@CONNECT` 连 SENLO/6 | SENLO/6 被自动置顶,SENLO/2 掉到第二 ❌ |
| 用户期望 | "我设的优先应该一直有效" |

根因是 `dap_config_add()` 里那句"新网络放最前"——它实现的是**最近使用优先(LRU)**,和用户想要的**显式优先**是两种语义,却共用同一个数组顺序。

### 1.2 方案:加一个 pin 标记

给 `dap_cfg_ap_t` 加 `uint8_t pin`,存在 NVS 里(`apN_pin`)。规则(2026-10-29 实现定稿,固件提交 `8aaac67`):

```
连接尝试顺序 = [所有 pinned 的,按它们原来的相对顺序] + [未 pinned 的,按 LRU]
@CONNECT 成功   → 物理置顶不变,但轮转走计算序,pin 推不倒
@PIN  idx=N on|off → 置位/清位(粘性,存 NVS)
@PRIO idx=N    → 只做物理置顶,不碰 pin(与 @PIN 语义分界)
```

实现要点:`dap_config_conn_physical(logical)` 做连接序号→物理下标映射,
`wifi_handle.ssid_change()` 的游标是逻辑序号。物理顺序继续表达"最近用过的
未 pin 网络优先",@CONNECT 的自动置顶逻辑一行没改。

**为什么不做成"整表排序"**:pinned 区段内部也要有先后,用整表排序会把
pinned/未 pinned 混在一起,判断"谁被保护"就得靠额外规则,越写越绕。
分段是两个独立区间,各自有序,语义干净。

**兼容性**:老 NVS 没有 `apN_pin` 键 → 读出来默认 0(全部未 pinned),行为和现在一致,不会因升级丢配置。`dap_config_add()` 对新条目显式清 pin,
防止整体后移时继承旧首条的固定优先。

**实测(2026-10-29)**:pin=1 重启保持;物理 idx=1 的 pinned 网络开机日志
`trying ssid[0/4]: SENLO/6 (pinned)` 第一个尝试;@REBOOT 触发的
`set_config failed: ESP_ERR_WIFI_STOP_STATE` 被 5c0c63c 的修复正确吞掉,
板子不再 panic。GUI 侧 111 项自检 + 真机 @PIN on/off→@LIST 全链路通过。

### 1.3 GUI 侧

「已保存网络」页改造:

```
┌──────────────────────────────────────────────────────┐
│ 刷新   置顶/取消置顶   上移   下移   删除  恢复出厂    │
├──────────────────────────────────────────────────────┤
│ #  优先  WiFi 名称          密码     连接顺序          │
│ 0   📌   SENLO/2           ***      1  (开机首选)     │
│ 1   📌   森龙大厅           ***      2                │
│ 2        SENLO/6           ***      3                │
│ 3        DAP               ***      4                │

```

- 「优先」列显示 📌;点「置顶/取消置顶」切换
- 「连接顺序」是**计算结果**,不是用户填的——让人一眼看懂"固件到底会按什么顺序试"

## 2. 环境集成:一个入口,三份工具

### 2.1 现状盘点(实测)

| 路径 | 形态 | 依赖 | 免驱动? | 授权 |
| --- | --- | --- | --- | --- |
| Keil µVision | `elaphureLink.Wpf.exe`(WPF GUI) + `DriverInstallHelper.exe` | .NET 4.7.2;往 Keil 装 AGDI 驱动 | 是(TCP 直连) | **BSD-2** |
| OpenOCD / VSCode | `openocd-elaphurelink\v0.4.0\bin\openocd.exe` + 1078 个 .cfg | 无(绿色) | 是(TCP 直连) | **GPL-2** |
| pyOCD / 通用 | `usbip-win\v0.3.6-dev\usbip.exe` + vhci 驱动 | **管理员 + 内核驱动** | 否 | **GPL-2** |

三份工具**已经在仓库里**,缺的不是工具,是**知道该开哪个、地址填什么、为什么连不上**。

### 2.2 方案:统一入口 + 自动配置

GUI 增加第 4 个标签页「调试接入」:

```
┌─ 调试接入 ───────────────────────────────────────────┐
│ 设备:dap-0.7.0 @ 192.168.0.125(通过 mDNS dap.local)│
│                                                       │
│ ┌─ Keil µVision ────────────────────┐ [启动] [✓已就绪]│
│ │ elaphureLink 1.4.0 · 免驱动        │                │
│ │ 地址将写入:dap.local               │                │
│ └───────────────────────────────────┘                │
│ ┌─ OpenOCD / VSCode ───────────────┐ [启动] [复制命令]│
│ │ openocd-elaphurelink 0.4.0        │                │
│ │ openocd -f interface/elaphurelink.cfg \             │
│ │         -c "cmsis-dap elaphurelink addr dap.local" \ │
│ │         -f target/stm32f1x.cfg                     │
│ └───────────────────────────────────┘                │
│ ┌─ usbip(给 pyOCD 等只认 USB 的)──┐ [挂载] [卸载]  │

│ └───────────────────────────────────┘                │
│                                                       │
│ ⚠ usbip 与 Keil/OpenOCD 抢同一个 DAP 会话,别同时用   │
└───────────────────────────────────────────────────────┘
```

关键实现点(都是**小工作量**,因为地址已经能被程序改写):

| 动作 | 实现方式 | 工作量 |
| --- | --- | --- |
| 把当前 IP 写进 elaphureLink | 直接改 `elaphureLink.Wpf.exe.config` 里的 `deviceAddress`(实测是可读写的普通 XML,`userSettings` 段) | 小 |
| 启动 elaphureLink | `subprocess.Popen`,`gui` 检测进程是否在跑 | 小 |
| 生成 OpenOCD 命令 | 拼字符串 + 一键复制到剪贴板;可选直接 Popen | 小 |
| usbip 挂载 | 复用现有 `attach_dap_hidden.vbs` 思路,`ShellExecute runas` 提权 | 中(要处理 UAC 取消) |
| 检测驱动装没装 | 查设备管理器里的 vhci 节点(`pnputil /enum-drivers` 过滤) | 中 |

### 2.3 用 mDNS 消掉"IP 会变"这个坑

实测 `dap.local` **能正常解析**:

```
$ ping dap.local
正在 Ping dap.local [192.168.0.125] ...
```

所以三份工具的地址**统一填 `dap.local`**,而不是写死 IP。这一条直接消灭了历史文档里反复出现的"IP 变了要重跑脚本"(`.253 → .187 → .125` 的踩坑记录)。

保留 IP 直填作为兜底:某些公司网络/路由器会拦 mDNS,那时在 GUI 里填 IP,同样会写进各工具配置。

### 2.4 明确不做的事

- **不做"一键全自动装好"**:usbip 要装内核驱动、elaphureLink 要往 Keil 目录塞 AGDI dll。静默装系统级组件是杀软重点关照对象,也会让"卸载不干净"变成售后负担。做成**明确的按钮 + 状态显示 + 失败可回退**。
- **不合并进程**:三个后端各自独立,唯一共享的是 GUI 这个入口。
- **不捆绑 Keil**:Keil 是商业软件,让用户自备。

## 3. 交付形态:三个包,不是一个包

### 3.1 授权现实(已核实)

| 组件 | 协议 | 能不能随包发 | 约束 |
| --- | --- | --- | --- |
| 本固件(windowsair 基线 + 我们的改动) | MIT | ✅ | 保留版权声明 |
| elaphureLink | **BSD-2** | ✅ | 保留版权声明 + 免责声明 |
| openocd-elaphurelink | **GPL-2** | ✅ 但**独立分发** | 附许可全文 + 提供源码获取方式 |
| usbip-win | **GPL-2** | ✅ 但**独立分发** | 同上 |
| flash_download_tool | 乐鑫专有 | ❌ **不发** | 让用户自己去官网下 |
| Keil µVision | 商业 | ❌ | 用户自备 |

**GPL-2 的实际含义**:GPL 的传染性针对"衍生作品"。只要你的 GUI **不链接** OpenOCD/usbip 的代码、只是**调用独立可执行文件**,你的 GUI 可以闭源。但 OpenOCD/usbip 本身必须**带着许可证和源码获取方式**发出去,不能只给个 exe。

> ⚠️ 这不是法律意见。真金白银卖之前,建议找个懂开源合规的人过一眼——但上面这条"独立进程不传染"是业界通行理解。

### 3.2 建议的包结构

```
WirelessDAP-1.0/
├── 无线调试器.exe              ← PyInstaller 打包的 GUI(闭源,你保有版权)
├── tools/                      ← 第三方,独立目录,各自带 LICENSE
│   ├── elaphureLink/           (BSD-2 + License.md)
│   ├── openocd-elaphurelink/   (GPL-2 + COPYING + 源码地址.txt)
│   └── usbip-win/              (GPL-2 + COPYING + 源码地址.txt)
├── firmware/
│   └── wireless_esp_dap.bin    ← 我们自己的固件(MIT)
├── 快速上手.pdf                ← 三页:接线 → 配网 → 开始调试
├── 许可与开源声明.txt          ← 汇总所有第三方协议
└── (不包含 Keil / flash_download_tool)
```

### 3.3 打包要点

- PyInstaller 6.22.0 本机已有,`--onefile` 可行。**注意 tkinter 要 `--collect-all tkinter`**,否则报缺 tcl/tk
- exe 未签名 → 首次运行 SmartScreen 会警告"未知发布者"。**这个绕不过去**,除非买代码签名证书(约 ¥1000-3000/年)。方案里如实告知用户,并在快速上手里写"点'更多信息'→'仍要运行'"
- 版本号/公司名写进 exe 资源,别留 `dap_config.exe`

## 6. B1/B2 实现记录(2026-10-28)

### 6.1 落地形态

新增 `tools/dap_backends.py`(442 行)做进程调度,GUI 增加第 3 个标签页「调试接入」。
**没有把任何第三方代码编进本程序** —— 全部走 `subprocess`,因此本程序不是
GPL 组件的衍生作品,可以闭源分发(§3.1 的前提成立)。

### 6.2 三个后端各自的形态

| 后端 | 能否无头 | 实现方式 |
| --- | --- | --- |
| OpenOCD | ✅ 完全无头 | `Popen` + `CREATE_NO_WINDOW`,stdout 管道逐行喂给日志页 |
| usbip | ⚠️ 一次动作 | `ShellExecuteW runas` 提权(复用现成 vbs 的思路) |
| elaphureLink | ❌ 无命令行模式 | WPF 程序,只能 `Popen` 起进程;地址写进它的 `.config` |

### 6.3 关键发现:OpenOCD 的"起来了"≠"连上了"

实测:**OpenOCD 只有在真正和目标芯片建立 SWD 会话后,才会打开 gdb 端口 3333。**
连不上目标时它照样跑着,只开 6666(tcl)和 4444(telnet),3333 永远不出现。

用户看到"运行中"却连不上 gdb,完全无从下手。所以加了 `gdb_ready()`:
嗅探日志里的 `Listening on port 3333`。GUI 据此区分三态:

- `已连上目标 · gdb :3333`(绿)—— 可以开始调试了
- `运行中,但还没连上目标芯片(查 SWD 接线)`(黄)—— 进程活着但没握手
- `已就绪,未启动`(灰)

轮询 6 次(约 12 秒)仍没等到 3333 时,主动弹出排查清单(SWD 四线/目标是否上电/
芯片选对没/复位脚)。

### 6.4 工具发现策略

开发机上第三方工具不在项目目录(在 `D:\ARMGCCTool\WirelessDebuggingtool\`),交付包里
应该在 exe 旁边。`tools_root()` 按序找,判据是**目录里真的有 openocd.exe** 而不是
"目录存在" —— 后者永远命中开发仓库自己的 `tools/`(它存在但只有源码)。

### 6.6 两个踩到的真实缺陷

**`pnputil` 输出编码**:中文 Windows 上是 GBK 不是 UTF-8。指定 `encoding="utf-8"`
会抛 `UnicodeDecodeError` 并让线程崩掉。改成取 bytes 后按 utf-8→gbk→cp936→latin-1
依次尝试解码。

**日志回调递归**:给 `OpenOcdBackend` 加 gdb 端口嗅探时,最初写成"把包装函数存回
`self.on_line`,包装里再调 `self.on_line`" —— 自己调自己,首行就无限递归。改成
用独立字段 `_user_on_line` 保存原始回调。

### 6.7 AT32 烧录:两条 OpenOCD 路,别混

**先说结论**:AT32 无线烧录**早就能做**,路径是 `usbip 桥接 + atopenocd`,
不是 elaphurelink。本项目 2026-10-26 已实测通过(506KB axf 擦+写+校验+复位)。

关键事实(2026-10-28 逐项核实):

| 构建 | 版本 | AT32 flash 驱动 | elaphurelink |
| --- | --- | --- | --- |
| `D:\ARMGCCTool\atopenocd` | 0.11.0+dev | ✅ `src/flash/nor/at32f4xx.c` | ❌ |
| `openocd-elaphurelink\v0.4.0` | 0.12.0+dev | ❌ 0 个 | ✅ |
| `atopenocd-build\openocd-puya` | 0.12.0-rc2+dev | ❌ 0 个 | ❌ |

**为什么不能互相替代**:flash 驱动是**编译进 openocd.exe 的 C 代码**,不是 cfg 脚本。
实测拿 elaphurelink 版加载 AT32 的 cfg:

```
$ openocd.exe -f interface/elaphurelink.cfg -s D:\ARMGCCTool\atopenocd\scripts \
              -f target/at32f403axG.cfg
Error: flash driver 'at32f403axx' not found
  at32f403axG.cfg:59: flash bank $_FLASHNAME $_CHIPNAME 0x08000000 ...
```

cfg 能借用,**驱动借不了**。字符串对比印证:elaphurelink 版里 `at32f403a` 只有 8 个
匹配(全是器件名,用于识别),`at32f403axx` 驱动 0 个。

**能力边界**:

| 目标 | elaphurelink 版 | atopenocd(经 usbip) |
| --- | --- | --- |
| 调试 STM32 | ✅ 免驱动 | ✅ |
| 烧录 STM32 | ✅ | ✅ |
| 调试 AT32 | ✅(内核级,不需 flash 驱动) | ✅ |
| **烧录 AT32** | ❌ `flash driver not found` | ✅ |

**曾考虑但不需要做**:给雅特力 fork 打 elaphurelink 补丁,做一个"既能无线直连又能烧
AT32"的 OpenOCD。核实后确认**没必要** —— usbip 这条路已经验证可用,而且补丁基线是
0.12、AT32 驱动在 0.11,版本错位会带来额外适配成本。

### 6.7.1 雅特力有没有 0.12 版?(2026-10-28 查证)

查了雅特力官方仓库(gitee `amoxu/openocd-at32`,36 个标签),结论是**没有**:

| 分支/标签 | configure.ac 版本 | AT32 驱动 |
| --- | --- | --- |
| `v0.12.0`(标签) | 0.12.0 | ❌ **没有** `at32f4xx.c` |
| `at32-dev`(分支,活跃) | **0.11.0+dev** | ✅ `at32f4xx.c` / `at32xx.c` / `at32qspi.c` |

**这是最容易误解的地方**:`v0.12.0` 标签是**上游 OpenOCD 的原样镜像**(仓库描述
"Official OpenOCD Read-Only Mirror"),不含雅特力的 AT32 驱动。AT32 驱动只在
`at32-dev` 分支上,而那个分支停在 0.11.0。

**0.12 有,AT32 也有,但两者从未同时出现过。** 本地 `D:\ARMGCCTool\atopenocd`
(0.11.0+dev, 2024-08)就是 `at32-dev` 这条线编译出来的。

**结论:不投入**。理由:
1. 雅特力自己没做 0.12,不存在"升级一下就好"的选项
2. 0.12 相对 0.11 对 AT32 烧录没有已知改进(AT32 驱动是雅特力自维护,与上游版本无关)
3. 真要升,应该是等雅特力自己出,而不是自己 fork 维护

若雅特力将来真迁移了,GUI 侧只需改 `find_atopenocd()` 的路径 —— 代码已按
"雅特力 fork"这个抽象做的,不用动逻辑。

### 6.8 网段不通是最常见的坑

实测踩到:PC 在 `192.168.0.x`,板子连了 SENLO/6 落在 `192.168.1.105`,TCP 3240 连不通。
表现是"点了挂载,卡住没反应"。

所以 `UsbipBackend.reachable()` 在挂载前先探 3240/1234 端口,不通就直接报:

> 最常见的原因:PC 和设备不在同一网段…… 排查:1. 配网页看设备连哪个 WiFi
> 2. 路由器可能开了客户端隔离 3. 换个和 PC 同网段的 WiFi

**为什么用 TCP 而不是 ping**:Windows 防火墙默认拦 ICMP,ping 不通不代表端口不通,
而 3240 才是真正要用的端口。

#### 6.8.1 mDNS 会返回过期缓存(实测踩到)

板子从 `192.168.0.125` 漂到 `192.168.1.105` 后,**`dap.local` 仍然解析成 .125**,
而那个地址已经没人应答。这会造成一种很迷惑的现象:

```
第一次测:  dap.local -> 192.168.0.125, 3240 可达 ✅  (板子当时确实在 .125)
十分钟后:  dap.local -> 192.168.0.125, 3240 超时 ❌  (板子已漂到 .105)
```

**同一句命令,同一个 IP,结果不同。** 用户会以为是"网络时好时坏"。

处理:`reachable()` 成功时把**实际测通的 IP** 报出来(`dap.local(192.168.0.125):3240
可达`);失败时的提示里把「mDNS 缓存过期」列为第一可能,并引导用户去配网页看设备
当前真实 IP。

#### 6.9.1 顺带发现的缺陷:秒退未被界面捕获

### 6.10 AT32 无线烧录端到端验证(2026-10-28 ✅)

前置:PC 连 SENLO/6(192.168.1.106),板子连 SENLO/6(192.168.1.105),同网段。
usbip 挂载成功(`successfully attached to port 0`,设备管理器出现
`Wireless ESP CMSIS-DAP`,状态 OK)。

| 步骤 | 结果 |
| --- | --- |
| atopenocd 识别 | ✅ 2 秒:`Cortex-M4 r0p1 processor detected` + gdb :3333 |
| flash 驱动 | ✅ 双 bank 各 512KB(`at32f403axx.bank1/bank2`) |
| 读(dump 512KB) | ✅ 125s(4.1 KiB/s);**注意 timeout 要给足 300s,否则静默截断** |
| halt/erase/write/verify | ✅ 擦 0.22s、写 2048B 1.24s、校验通过 —— **全程 WiFi** |
| 恢复原状 | ✅ 测试扇区擦回空白;bank2 未被波及(逐字节核查过) |

**dump 截断教训**:第一次 dump 用了 `timeout 120`,无线读 512KB 实测要约 125s,
openocd 被杀在半路只留下 484KB 的文件,不报任何错误。**大块 dump 的超时必须按

四张卡片就是这条链的产品化形态。

#### 6.10.1 顺带修掉的固件 panic(严重)

真机复现:
```
assert failed: esp_wifi_set_config(ESP_IF_WIFI_STA, &wifi_config)
abort() was called at PC 0x40382177 on core 0
```

根因:`ssid_change()` 用了 `ESP_ERROR_CHECK`。它在 STA_DISCONNECTED 回调里
被调用,那一刻驱动正从断开态往重连态过渡,`esp_wifi_set_config` 会返回
`ESP_ERR_WIFI_STATE`,于是整板 panic。快速连续 @REBOOT / 断连重连的窗口期
必现。**这正是此前"IP 时变、端口时通时断"怪象的根源之一。**

修复(commit 5c0c63c):失败只 LOGW 跳过本轮,等下一个 DISCONNECTED 事件
再试。修复后连续 @REBOOT 不再 panic。

#### 6.10.2 操作注意事项(写进用户手册)

- **板子插着 CH343 口(COM19)时,对 COM18 的任何 open/close 都可能触发复位**;
  调试期间只留 native USB,避免网络反复掉线
- usbip 挂载后**不要再动串口**,复位会断桥
- 挂载失败重试前,先看可达性提示(网段/mDNS 缓存)
- 目标芯片 flash 低半区有真实程序,**测试写入要用确认空白的扇区**,
  并且先 dump 备份

### 6.11 A1/A2 优先标记落地 + GUI 两个真机坑(2026-10-29 ✅)

**固件**(提交 `8aaac67`):pin 标志 + `dap_config_conn_physical()` 计算序 +
`@PIN idx=N on|off` + `@LIST` 带 `pin=` 字段,设计见 §1.2(已按实现修订)。
真机验收:pin 重启保持、pinned 网络开机第一个尝试、panic 修复在 @REBOOT
断连窗口实战生效。**坑**:`@PIN` 的 on/off 是裸 token 不是 `key=value`,
`param_get` 取不到,首版回 400 usage —— 固件和 GUI MockTransport 各自修了
同样的一处。

**GUI**(自检 111 项全过,真机 E2E 通过):

1. **DTR/RTS 时序(重要)**:`Serial(port, ...)` 构造即打开,Windows 驱动
   先按默认电平拉 DTR/RTS → 板子被踹复位;之后再 `setDTR(False)` 来不及,
   实测 CDC 端点起不来,**write 永远 Write timeout 而读日志正常**(RX 有
   启动横幅、TX 全部 408)。修法:先逐项配置 `dtr=False; rts=False` 再
   `open()`,驱动从头到尾不产生脉冲。acccom 工具(打开前声明)能用的
   原因正是它没踩这个时序。
2. **wait_ready 双路径**:原来死等启动横幅 `command channel ready`;
   DTR 修复后开串口不再复位、板子已在跑,横幅永远不来 → 就绪判定改成
   "横幅出现 **或** @PING 直接应答"。
3. 界面:「已保存网络」加「固定」列(📌)与「固定优先/取消固定」按钮,
   置顶/删除的取列索引同步挪位;置顶对 pinned 行提示"已固定,不用置顶"。




## 5. 需要你拍板的三个点

1. **优先语义**:要不要把 `@CONNECT` 的"自动置顶"**彻底去掉**,改成纯 LRU 记录但不动用户排的序?还是保留"未 pin 的按最近使用排"?我倾向后者(见 1.2),但那意味着 pinned 的条目永远不动,有人可能觉得"我刚连的这个怎么没排前面"。
2. **usbip 要不要默认装**:它是唯一需要管理员+内核驱动的,也是杀软最容易拦的。可以做成"默认不装,点了才装",或者干脆**卖的时候只承诺 Keil + OpenOCD 两条路**,usbip 作为进阶功能不写进承诺。
3. **签名证书**:不买 → SmartScreen 警告;买 → 约 ¥1000-3000/年。卖给同事可以不管,真上架卖得考虑。
