# 方案对比与选型

> 状态:**已选定路线 A(2026-10-25)**。调研依据见 [现有方案调研.md](现有方案调研.md)。

## 候选路线对比

### 先澄清:传输层"TCP 直连"≠ 路线 B

"走 TCP"和"自己写协议"是两件事,分层看:

| 层 | 内容 | 现成程度 |
| --- | --- | --- |
| IDE 层 | Keil / OpenOCD / pyOCD | 现成 |
| 协议层 | CMSIS-DAP(ARM 标准,官方开源实现) | 现成 |
| 传输层 | USBIP(模拟 USB,任何 IDE 免改动,PC 要装驱动)vs TCP 直连(免驱动,但每个工具要有对应客户端) | 都有现成实现 |
| 固件硬件层 | CMSIS-DAP 命令处理 + SWD/JTAG 时序 + SPI 加速 | Espressif `esp_dap` 组件现成 |

- 路线 A 中的 **elaphureLink 就是 TCP 直连**:Keil 插件、openocd-elaphurelink 都走纯 TCP,免驱动——选路线 A 已经拿到了 TCP 路线的核心好处
- 路线 B 与路线 A 的真正差别:不站在 windowsair 整套固件的肩膀上,而是自己从 `esp_dap` 起步拼装;取舍在 IDE 覆盖面(见路线 B 短板)

### 路线 A:windowsair/wireless-esp8266-dap 二次开发(推荐起点)

- **做法**:固件直接用开源实现(或其活跃分支 kerms/wireless-esp32-tools),先开发板验证,再画专用 PCB
- **PC 连接方式**:优先 elaphureLink 直连(Keil 插件 / openocd-elaphurelink,免驱动);USBIP 作为兜底兼容模式
- ✅ 站在 4 年+ 成熟项目肩膀上,Keil/OpenOCD/pyOCD 全兼容,自带 OTA、串口透传、参考硬件
- ✅ 硬件极简:单芯片 + 晶振 + USB-C 电源 + 电平转换,ESP32-C3 整机 BOM 可压到 ¥20 以内
- ⚠️ 二次开发要读懂 USBIP/CMSIS-DAP 协议栈;个性化功能(配网、按键、指示灯)需要自己加
- 适合:想尽快用上、以后再做自己的差异化功能

### 路线 B:纯 TCP 方案(拼装现成件,并非全部自研)

- **做法**:固件端用 Espressif 官方 `esp_dap` 组件(CMSIS-DAP 协议处理、SWD/JTAG 时序、SPI 加速都是现成的)+ 现成的 TCP 传输方式;PC 端复用 OpenOCD 内置的 `remote_bitbang` 驱动,或 bkuschak 的 cmsis-dap-tcp 后端
- **实际工作量不大**:真正要自己写的只是"胶水"——把 esp_dap 的 DAP 命令接到 TCP 收发上;`remote_bitbang` 协议本身只有几个 ASCII 命令,固件端几十行就能实现
- ✅ 无驱动、跨平台最干净,全程理解每一层,学习价值大,代码量可控
- ⚠️ 真正的短板是**工具覆盖面**而不是工作量:Keil 只能靠 elaphureLink 插件(用它就等于回到路线 A 的连接方式),自写 Keil 插件则接口文档少、难度高;pyOCD 只认 USB CMSIS-DAP,纯 TCP 模式下用不了
- ⚠️ 性能:remote_bitbang 逐位传输,只适合单步调试、烧录体验差;cmsis-dap-tcp 后端快一些但依赖非主线的 OpenOCD 补丁
- 适合:只调 OpenOCD 能覆盖的目标、以学习为目的,或作为路线 A 之外的补充实验

### 路线 C:双板桥接(真 USB 设备)

- ✅ PC 侧兼容性最好(真 USB CMSIS-DAP,任何 IDE 零配置)
- ⚠️ 两块板、成本和体积翻倍,只把"USB 线"变成"WiFi",整体体验不升反降
- 适合:特殊场景(如 PC 驱动管控严格无法装任何东西)

### 路线 D:Pico W / RP2040

- ⚠️ 没有成熟的开源无线 DAP 实现,等于从零开始;直接排除

## 已选定:路线 A(2026-10-25 讨论)

以 windowsair/wireless-esp8266-dap 生态为基础做二次开发。同日确认的配套决策:

- **主控芯片**:ESP32-C3 与 ESP32-S3 开发板各一块,实测对比(速度/稳定性/温度/尺寸)后再定 PCB 主控
- **调试环境**:Keil MDK、OpenOCD + VSCode、pyOCD 都要用,另有其他目标芯片
  - 两种连接模式都要支持:Keil 走 elaphureLink 直连(免驱动);OpenOCD/pyOCD 走 usbip-win 虚拟 USB(通用兼容),openocd-elaphurelink 补丁版作为免驱动备选
- 分步计划:
  1. **原型验证**:两块开发板刷官方 release 固件,接目标板跑通各调试环境,实测烧录速度与稳定性
  2. **自制硬件**:根据实测结果定主控,画专用 PCB

## 决策记录

- [x] 技术路线:开源方案二开(路线 A)
- [x] 主控芯片:原计划 C3、S3 都测;2026-10-25 确认手头只有一块通用 ESP32-S3 核心板 → 先用 S3 验证,S3 达标则 PCB 直接选 S3(原生 USB 可扩展双模),C3 仅在 S3 不达标时补购对比
- [x] 上位机:Keil + OpenOCD + pyOCD 全覆盖,另有其他目标
- [x] **产品定位(2026-10-27 变更)**:从"自家自用"改为 **给同事用 / 开源发布 / 小批量卖几块** → 触发配网与 AP 模式成为必做项,方案见 [产品化方案-配网与双模网络.md](产品化方案-配网与双模网络.md)
- [x] **网络形态(2026-10-27 第二版拍板)**:两个模式、**不自动切换**
  - **STA(日常默认)**:与已验收的现状完全一致,一行不改
  - **AP(仅命令切换)**:设备自开热点 `DAP-<MAC4>`/`12345678`,板地址 192.168.4.1,给"没有路由器"的场景用;**只有 `@MODE AP` 命令能进入**,连不上路由器也不会自动降级
  - 关键约束:IDF 文档明确 `esp_wifi_scan_start()` 仅支持 Station 或 Station+AP 模式 → **纯 AP 模式下不能扫描**,所以配网固定在 STA 模式进行,AP 不承担配网职责
  - 传输层零改动:`tcp_server.c:57` 与 `uart_bridge.c:176` 均绑 `INADDR_ANY`,AP 起来后 3240/1234 自动可用;AP 的 DHCP 服务器由 IDF 固有配置自动启动
- [x] **配网方式(2026-10-27 第二版拍板)**:由 **PC 端 Python GUI 工具经 USB(COM18)与板子通讯**完成,**不做板载网页、不做手机 App**
  - 理由:配网时板子还没上网,没有 IP 可连,命令通道只能是物理链路;USB 又是烧录口,零额外硬件
  - 命令集:`@PING @STATUS @SCAN @CONNECT @MODE @LIST @DEL @FACTORY @REBOOT`
  - 配网体验:自动扫描 → 列表显示 SSID/RSSI/加密 → 选一个填密码 → 区分 201 找不到 AP / 202 密码错 / 204 握手超时
  - 配置存 NVS;编译期 SSID 列表降级为出厂默认
- [x] 无线串口透传(UART Bridge):**已实现并验收**(v3,TCP:1234,行参协商 `baud[E|O|N]`)
- [x] **OTA:推后到下一阶段(2026-10-27)**,但**已确认技术上完全可行(2026-10-28 实测)**。当前是 `CONFIG_PARTITION_TABLE_SINGLE_APP=y`,分区只有 `nvs/phy_init/factory(1M)`,**没有任何 OTA 分区**,`corsacOTA.c:689` 的 `esp_ota_get_next_update_partition()` 实际不可用;切 `partitions_two_ota.csv`(factory 1M + ota_0 1M + ota_1 1M)即可。**板载 Flash 实测 16MB**(`esptool flash_id`,厂商 0x68 / 设备 0x4018),空间绰绰有余,不是瓶颈;原"2MB 太紧可能放弃"的顾虑来自 sdkconfig 保守值,已排除
