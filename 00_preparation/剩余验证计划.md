## G. 无线串口桥(2026-10-27 新增功能,**v3 已上线**)

启用 windowsair 自带 uart_bridge(上游无 S3 分支,自补 UART1/**GPIO17=TX、GPIO18=RX**,避开 USB 的 19/20、SWD 的 11/12),`USE_UART_BRIDGE=1`,**TCP:1234 ↔ 目标串口**,3.3V 直连共地。SWD(usbip 3240)与串口桥(1234)是独立任务,可同时无线烧录 + 调串口。**固件 v3 md5 0cf8c045(656,640 字节),归档已同步**。

**行参协商协议**——连接后首包发 `<baud>[E|O|N]`(如 `19200E` = 19200 8E1),桥自动切波特率+校验位;纯数字等价 8N1。默认 115200 8N1。**S3 的 sdkconfig 把 console 路由到 USB-Serial-JTAG,COM18 能看全部 IDF 日志**(含 `UART: change line:19200 8E1` 协商实锤),不需要 CH343。

**v3 槽位释放修复**(v1/v2 的僵尸槽位根治):
- FIN(空 netbuf)/recv 错误(含 ERR_CLSD)/write 失败 三条路径都会正确释放槽位;事件循环改**指针比较分发**(监听=本地 `nc`、活动=`uart_netconn`、其余一律不 deref 丢弃)——修掉了一个被 v3 第一版激活的上游 use-after-free 竞态(清理后队列残留事件指向已删 netconn)
- **验收 5/5**:基线/FIN 后重连/RST 后重连/19200E 协商存活/正常关闭后槽位回收 全部 accepted
- **已知边界:busy 窗口**——断开后 ~200ms 内新连接仍会被踢(FIN 处理延迟,一个 tick);acccom 重连遇踢等 300ms 重试一次即可
- 固件带运维日志(accept/kicked/FIN/recv err/write fail/stale),COM18 可观测

- **目标参数已实锤:JJ400 = 19200 8E1**(全参数扫描:仅 19200 有连续数据流,校验 E 通过 O 全无,其余波特率全静音——参数精确匹配指纹);**载荷为二进制协议**(6.6% 可读,大量 0x00),解码归 s403-AT 侧对照有线录制确认
- 人工用法:PuTTY Raw 连 `192.168.0.125:1234`,连上先发 `19200E` 回车
- agent(acccom):TCP 端点 open 时首包发 `19200E\n`;异常退出必须关 socket(桥已能自清理,但干净关闭仍是最优);parity=0(纯数字)对 v1/v2/v3 通吃

### 操作教训(esptool / COM 口 / 复位)

- 烧录只用 native USB(USB-Serial-JTAG);**CH343 那个 USB 口插着会把芯片拽进下载模式**(其 DTR/RTS 经自动下载电路扰动 boot,用户实测)
- esptool v3.3.2 在 USJ 上的"硬复位"(RTS 脉冲)必然进下载模式(rst:0x15 USB_UART_CHIP_RESET),与 GPIO0/OPTION1 无关(两者均读寄存器验证正常);**按板上 RST 键即可正常引导**,拔插 USB 亦可;`--after soft_reset` 仅支持 ESP8266
- esptool.exe 不在 PATH:用 venv python + `D:/Espressif/frameworks/esp-idf-v4.4.2/components/esptool_py/esptool/esptool.py`;v3 语法是下划线(`write_flash`/`read_mem`,不是 `write-flash`/`read_reg`)
- 读回校验按实际 bin 大小(本次 0xa01f0 = 655,856B,别按 0xA0000 截断);cmp 逐字节对比比 md5 更能暴露"截断造成的假不一致"
